# Authoring practice exams

A practice exam is a set of **10 single-choice questions, 4 options each, one correct, 1 point each, no penalty**. The sets are
`easy-01 … easy-07`, `medium-01 … medium-07`, `hard-01 … hard-07` (7 per tier, 210 questions per language): every set has a single difficulty. Sources live in
`tools/theory/exams/<id>.txt` (English) and `tools/theory/exams/es/<id>.txt` (Spanish translation of the same set).
Everything about question syntax is in `THEORY_AUTHORING.md`; this file only adds what is specific to exams.

## What the sets are for

They rehearse the **theory part of the real exam** (course "Sistemas Operativos", topic 1: shell, files, permissions, processes,
scripting, users, boot). The real test is 4 options, one correct, "which statement is true / false", "what does this command print",
"which command does X", sometimes "none of the other answers". The questions must be **original**: test the concepts of the course
slides in your own words and scenarios. Never copy or lightly reword a scenario from the reference exams used to calibrate difficulty (kept outside the repo;
`EXAMS_REF=<dir> node tools/exam_check.js` rejects close matches) and do not repeat what the 13 theory collections in `tools/theory/*.txt` already ask.

## Difficulty (what a tier means)

The reference exams set the bar: **easy is not trivia**. An easy question is one a student who attended the course answers in under
30 seconds, but it still needs a small piece of reasoning (read a short command, apply one rule) and its wrong options are the
classic confusions (`>` vs `>>`, `-v` vs `-c`, `.` vs `..`, hard link vs symbolic link).

| tier | what the student must do | typical shape |
|------|--------------------------|---------------|
| easy | one concept, one rule applied to a 1–3 line example; ≈ 30 s | which option / command does X; which statement is true; what one command prints; a definition |
| medium | combine two facts or trace 2–3 steps; ≈ 60–90 s | trace a short pipeline or redirection; relative paths after a `cd`; `umask` / `chmod` arithmetic; `find` tests; a FALSE statement hidden among four near-true ones |
| hard | interacting details and traps; ≈ 2–3 min | subshell vs `source` (cwd, variables, `$$`); quoting + expansion + redirection together; order of redirections; directory + file + owner/group permission checks; "find the bug"; one correct statement where the other three are wrong by a single detail |

Rules for every tier:

- Exactly one defensible correct answer. If an expert could argue for a second option, rewrite the question.
- Wrong options are plausible and about as long and specific as the right one; no joke options. The right option is not always the longest.
- Test knowledge from the course (the slides in `course-material/` and what a student can check in the lab), not trivia about one distro.
- Every command output, error message, exit status and permission result you state must have been **run in the lab**.
- Do not write "all of the above", "both a and b", "the previous answer". Options are shuffled. For "none of the other options" write it as the **last** option and mark it pinned: `(+!)` if it is the correct one, `(-!)` if it is wrong. Use it in at most 1–2 questions per set.
- Every option has a one-line explanation (`:: ...`) saying why it is right, or what it would actually do / where it would be right. These are shown in the review of an attempt.
- Questions stand alone: no "see the previous question".

## Format of an exam file

```
@@exam medium-03 | Medium exam 3          first line; id = file name = <tier>-NN
@@tier medium
@@about
One or two sentences (optional).

@@q single | Short unique title          the title is only shown in the review; it must not give the answer away
@@topic permissions                       REQUIRED: the topic of this slot (see blueprint)
Question text in markdown (code in backticks or fenced blocks).
(+) right option :: why
(-) wrong option :: why
(-) wrong option :: why
(-) wrong option :: why
@@note                                    optional takeaway shown after answering
```

The Spanish file has the same questions in the same order with the same right/pinned positions (`(+)` in the same line number among the
options), without `@@tier` or `@@topic`. Translate text, options, explanations and notes; keep commands and code unchanged. The first line is
`@@exam <same id> | <Spanish title>`.

## The blueprint (what to write in each slot)

`tools/theory/exams/blueprint.json` (generated by `node tools/exam_blueprint.js 7`, do not edit by hand; sets that already have a source file keep their slots, so the file can be regenerated safely) says, for every set, what each of
the 10 questions is about: the **topic** (the compiler enforces it), the **subtopic** to test and a **suggested style**. Question N of your
set must be about the topic of slot N and test the subtopic given. The style is a suggestion: adapt it when it does not fit.
This is what makes coverage even across all the sets, so do not swap slots.

Topics: `shell-help`, `jobs-procs`, `files-fs`, `permissions`, `filters`, `grep-regex`, `find`, `expansion-vars`,
`redirection-pipes`, `scripts`, `users-sessions`, `boot-systemd`, `logs-cron`.

## Workflow for one set

1. Read your rows of `blueprint.json` and the course slides for those subtopics (`course-material/` if present, otherwise the existing theory collections as topic reference).
2. Write `tools/theory/exams/<id>.txt`. Verify every claim in the lab: `LAB_INSTANCE=<your-name> ./lab bash -c '...'` (your own container, so you never block anybody else).
3. Build **only your file**: `node tools/build_theory.js tools/theory/exams/<id>.txt` (fixes syntax, 4 options, pinned rules, topics, the blueprint; nothing is written on error).
4. Duplicates: `node tools/exam_check.js tools/theory/exams/<id>.txt` must report 0 too close. Rewrite what it flags (and look at the warnings).
5. Write `tools/theory/exams/es/<id>.txt` and build it: `node tools/build_theory.js tools/theory/exams/es/<id>.txt`.
6. Do not touch other files, do not commit.

# Script practice exams

Besides the theory sets there are **script practice exams**: one bash script each, graded out of 10 by objectives, shown under *Coding exercises → Practice exams* on the home page. The plan is 7 per tier (`easy-01 … easy-07`, `medium-…`, `hard-…`); today there is one per tier (`easy-01`, `medium-01`, `hard-01`). Imported packs can add more of their own (`web/import-prompt.md`, kind `scriptexam`). They are a different thing from the
theory sets (own sources, API `/api/sexams`, routes `#/sexam/…` and storage `.progress/script-exams/`), even though the ids look alike.

Calibration (an authoring choice: the real October duration is not known). The June exam's first exercise (`deploy_bins.sh`, 3 of 10 points in a
100-minute exam, i.e. about 25 minutes of work; it is exercise 1801 of the tracks) is the reference:

| tier | what the script asks | about |
|------|----------------------|-------|
| easy | optional argument, 2–3 validated error paths with exit codes and stderr messages, one simple core task, a few special cases | 10–15 min |
| medium | the June scope: argument errors with distinct codes and a usage message, a default, parsing or `find` plus sorting/arithmetic, a summary, special cases | 25 min |
| hard | medium plus interacting traps: side effects with a message, collisions, files that cannot be processed (count + final exit code), names with spaces, ordering rules | 35–40 min |

Sources are `tools/src/script-exams/<id>.txt` (format in `tools/build_script_exams.js`); `node tools/build_script_exams.js` writes
`script-exams/<id>_<slug>/{README.md,README.es.md,check.sh,meta.json}` and `solutions/script-exams/<id>_<slug>.sh`. Statements are bilingual
(Theory language toggle). Rules:

- Original scenarios; do not reuse or paraphrase the course exams, and check `tools/src/18_exam*.txt` so a track exercise is not posed again.
- The statement ends with a "Don't forget" list whose items are the objectives and their points (the points add up to 10).
- `@@check` is a normal checker spec (`lib/engine.sh`) plus `CASE_OBJ=( ... )`: one objective id per `ARGS` entry. A case that fails
  anything (stdout, exit code, stderr presence, files) loses its objective's share: points = weight × passed cases / cases of that objective.
  Isolate objectives with the fixture (a directory per behaviour) and with state prepared inside the case string (`'dups $(pre_q)'`,
  where `pre_q` is a function of the spec), so a wrong implementation of one feature does not fail every case.
- Every ARGS case must expect observable output, or a do-nothing script would pass it.
- Deterministic fixtures: use `rand`/`pick`/`word`, fixed `touch -d "@epoch"` times, never `$RANDOM` or wall-clock times.
- Add `tools/src/script-exams/partials/<id>.<name>.sh` with a first line `# expect: LOW..HIGH`: a plausible partial solution (for instance
  correct core logic without argument checks) whose score range is asserted.
- Run `./lab tools/validate_script_exams.sh` inside a lab instance: the reference must score 10, a do-nothing script at most 0.5, and each
  partial its expected range. Also run `./lab tools/validate.sh` after touching `lib/engine.sh` (grading is additive; the checker output is unchanged).
- Tests of the web UI must use a scratch progress directory: `LAB_PROGRESS=/tmp/scratch node web/server.js` (the engine honours it too),
  never the real `.progress`.

@@collection 01_shell | Fundamentos de la shell y cómo pedir ayuda
@@about
Qué es una shell y cómo ejecuta una línea, mandatos internos frente a externos, PATH, valores de retorno, separadores de mandatos, edición de línea y cómo buscar ayuda con man, info y less.

@@group Qué es una shell
@@q single | Papel de la shell
¿Qué frase describe mejor lo que hace una shell como `bash`?
(+) Es un programa que lee mandatos en texto, los interpreta y lanza otros programas por ti; además permite programar scripts. :: Ese es todo su trabajo: una interfaz de texto entre tú y el sistema operativo, con programación (variables, `if`, bucles) por encima.
(-) Es la parte del núcleo que planifica los procesos, gestiona la memoria y habla con el hardware en nombre de cada programa. :: Eso es el propio núcleo (kernel). La shell es un programa normal de espacio de usuario; pide cosas al núcleo mediante llamadas al sistema.
(-) Es el entorno de escritorio gráfico que dibuja ventanas y menús y te permite lanzar programas con el ratón. :: Eso lo hace un entorno de escritorio. Una ventana de emulador de terminal solo *aloja* una shell; la shell no dibuja ventanas.
(-) Es un compilador que traduce cada script a un ejecutable binario antes de ejecutarlo, de modo que los scripts nunca se interpretan. :: Los scripts de shell se interpretan línea a línea. No se compila nada por adelantado.
@@note
El núcleo, la shell y la ventana del terminal son tres cosas distintas: la shell es un programa normal que habla con el núcleo por ti.

@@q single | Shell frente a terminal
¿Qué relación hay entre un emulador de terminal (p. ej. `xterm`, GNOME Terminal) y la shell que se ejecuta dentro?
(+) El emulador solo aporta la ventana, la entrada de teclado y la salida de texto; la shell es otro programa que se lanza dentro. :: Correcto. Puedes ejecutar `zsh` o `dash` dentro del mismo emulador y la ventana no cambia en nada.
(-) Son el mismo programa, así que cambiar la ventana del terminal por otra también cambia tu shell y su configuración. :: Son programas distintos. Cambiar de emulador deja tu shell (y su configuración) como estaba.
(-) El emulador de terminal interpreta los mandatos y lanza programas, mientras que la shell solo dibuja el texto en pantalla. :: Es al revés. La shell analiza y ejecuta mandatos; el emulador solo muestra caracteres y reenvía las pulsaciones.
(-) La shell solo funciona dentro de un emulador de terminal gráfico; por SSH o en una consola de texto no hay shell. :: En una consola de texto (tty) y por SSH también obtienes una shell; no hace falta ningún emulador gráfico.

@@q multi | Shells de la familia Unix
Marca todos los programas que son intérpretes de mandatos (shells) en sistemas tipo Unix.
(+) `bash` :: La Bourne-Again Shell, la predeterminada en la mayoría de distribuciones Linux.
(+) `ksh` :: La Korn shell, otra shell clásica de estilo Bourne.
(+) `tcsh` :: Una derivada de la C shell, con una sintaxis distinta de la de bash.
(-) `xterm` :: Un emulador de terminal: dibuja una ventana y ejecuta una shell dentro, pero no es un intérprete.
(-) `less` :: Un paginador para leer texto pantalla a pantalla.

@@q fill | Símbolo del prompt por defecto
Para un usuario normal, bash suele terminar el prompt con `{{$}}`; para root lo termina con `{{#}}`.
(x) > :: `>` es el prompt de *continuación* (PS2), que aparece cuando un mandato está incompleto, no el prompt normal.
@@note
El `#` de root es un aviso visual de que estás trabajando con privilegios ilimitados.

@@q order | Qué hace la shell con cada línea
Ordena los pasos del ciclo interactivo de la shell.
(>) Mostrar el prompt :: La shell indica que está lista para recibir un mandato.
(>) Leer una línea escrita por el usuario :: No puede analizar nada hasta que la línea existe.
(>) Analizar la línea (separarla en palabras, expandir, localizar redirecciones) :: El análisis y la expansión tienen que ocurrir antes de poder lanzar nada.
(>) Ejecutar el mandato o mandatos y, normalmente, esperar a que terminen :: Solo cuando la línea está entendida se puede lanzar el programa; en primer plano la shell espera.
(>) Volver a mostrar el prompt :: El ciclo se repite hasta que la shell termina.

@@q single | Varios mandatos en una línea
¿Qué imprime `echo uno; echo dos`?
(+) `uno` y `dos` en líneas separadas; el segundo mandato se ejecuta cuando termina el primero. :: `;` separa mandatos, que se ejecutan uno tras otro.
(-) `uno; echo dos` en una sola línea, porque todo lo que va detrás del primer `echo` se trata como su argumento. :: Un `;` sin comillas es sintaxis de la shell, no texto, así que la línea se divide en dos mandatos.
(-) Un error de sintaxis, porque en la shell cada línea de entrada solo puede contener un mandato. :: Se permiten varios mandatos por línea; `;` es precisamente el separador para eso.
(-) Solo `dos`, porque la salida del último mandato sobrescribe en pantalla la salida del primero. :: La salida se escribe en el terminal, no se guarda; no se sobrescribe nada.

@@q single | Entrecomillar un punto y coma
¿Cuál es la salida de `echo me gusta bash ";" mucho`?
(+) `me gusta bash ; mucho` :: Las comillas convierten `;` en texto normal, así que se pasa a `echo` como argumento.
(-) `me gusta bash`, seguido del error `mucho: command not found` :: Eso pasaría sin comillas; entre comillas `;` ya no termina el mandato.
(-) `me gusta bash mucho` :: `echo` imprime todos los argumentos que recibe, incluido `;`. Las comillas solo impiden que la shell lo interprete.
(-) Un error de sintaxis cerca de `;` :: Un `;` entre comillas es solo un carácter; el analizador no tiene nada de qué quejarse.

@@group Mandatos internos y externos
@@q single | Interno frente a externo
¿Cuál es la diferencia esencial entre un mandato interno (builtin) y uno externo?
(+) Un mandato interno está implementado dentro de la propia shell; uno externo es un fichero ejecutable aparte que la shell debe encontrar y lanzar. :: Correcto: un mandato interno se ejecuta como una función de la shell; uno externo necesita un proceso nuevo y un fichero en disco.
(-) Un mandato interno siempre se escribe más rápido, mientras que uno externo siempre hay que escribirlo con su ruta completa. :: No tiene que ver con cómo se escribe; los mandatos externos se encuentran a través de `PATH` sin ruta completa.
(-) Un mandato interno solo se puede usar dentro de scripts, mientras que uno externo solo se puede usar de forma interactiva en el prompt. :: Los dos tipos funcionan en ambos sitios.
(-) Un mandato interno siempre se ejecuta con privilegios de root, mientras que uno externo solo tiene los privilegios del usuario actual. :: Los privilegios dependen del usuario que lanzó la shell, no del tipo de mandato.

@@q sort | ¿Interno o externo?
@@buckets Interno | Programa externo
Clasifica cada mandato tal y como suele encontrarse en bash en Linux.
(Interno) `cd` :: Tiene que cambiar el directorio de trabajo del propio proceso de la shell, así que no puede ser un programa aparte.
(Interno) `jobs` :: Lista los trabajos de la shell actual, información que solo tiene la shell.
(Interno) `fg` :: Reanuda uno de los trabajos de la shell; un proceso hijo no podría hacerlo.
(Programa externo) `ls` :: Un programa aparte, normalmente `/usr/bin/ls`.
(Programa externo) `mkdir` :: Un programa aparte que pide al núcleo que cree un directorio.
(Programa externo) `grep` :: Un programa filtro independiente.

@@q single | Por qué cd es interno
¿Por qué `cd` no puede funcionar como un programa externo normal?
(+) El directorio de trabajo es propio de cada proceso, así que un `cd` externo solo cambiaría el suyo y después terminaría. :: Un proceso hijo no puede cambiar el directorio de trabajo de su padre, así que el mandato tiene que ejecutarse dentro de la shell.
(-) Porque `cd` necesita privilegios de root para poder leer el contenido de los directorios de otros usuarios. :: No necesita ningún privilegio extra; el acceso sigue los permisos normales del directorio.
(-) Porque en `/bin`, donde deben estar todos los mandatos externos del sistema, ya no cabe ni un binario pequeño más. :: El tamaño es irrelevante. La razón es el aislamiento entre procesos.
(-) Porque `cd` es una palabra reservada del lenguaje C y no se puede usar como nombre de programa. :: Solo coincide el nombre; no tiene ninguna relación con C.

@@q multi | Identificar un mandato
¿Qué mandatos te pueden decir si `ls` es un mandato interno, un alias o un fichero, y dónde está ese fichero?
(+) `type ls` :: Un mandato interno de bash que indica cómo se interpretaría el nombre (alias, interno, palabra reservada o fichero).
(+) `which ls` :: Busca en el `PATH` e imprime el primer ejecutable que encuentra, aunque no sabe nada de internos ni de alias.
(+) `whereis ls` :: Busca el binario, su página de manual y sus fuentes en ubicaciones estándar.
(-) `whatis ls` :: Solo imprime la descripción de una línea del manual; no dice nada de dónde está el mandato.
(-) `apropos ls` :: Busca una palabra clave en las descripciones de las páginas de manual.

@@q single | Lo que revela type
Al ejecutar `type cd` en bash se imprime `cd is a shell builtin`. ¿Qué imprimiría con más probabilidad `type ls` en un sistema típico?
(+) `ls is /usr/bin/ls` (o la descripción de un alias, si existe uno) :: `ls` es un fichero externo que se encuentra a través de `PATH`.
(-) `ls is a shell builtin`, igual que `cd`, porque los dos son mandatos básicos :: `ls` no está implementado dentro de bash.
(-) `ls: command not found`, ya que no está garantizado que `ls` esté instalado :: `ls` existe en cualquier sistema Linux.
(-) `ls is a shell keyword`, como `if` o `while`, que también son reservadas :: Las palabras reservadas son cosas como `if`, `for`, `while`; `ls` es un mandato normal.

@@q single | Interno y también en disco
En un Linux típico, `type -a echo` lista tanto `echo is a shell builtin` como `echo is /usr/bin/echo`. ¿Qué ocurre al escribir `echo hola`?
(+) Se ejecuta el interno, porque bash busca los mandatos internos antes de recorrer el `PATH`. :: Los internos tienen prioridad sobre los ficheros con el mismo nombre.
(-) Se ejecuta el fichero `/usr/bin/echo`, porque los ficheros en disco siempre tienen prioridad sobre los internos. :: Es justo al revés.
(-) Bash te pregunta a cuál te refieres. :: Bash nunca pregunta; el orden de búsqueda es fijo.
(-) Se ejecutan los dos y el texto sale dos veces. :: Solo se usa la primera coincidencia en el orden de búsqueda.

@@q fill | Búsqueda del nombre de un mandato
Cuando escribes el nombre de un mandato sin barra, bash encuentra el programa externo recorriendo los directorios que aparecen en la variable `{{PATH}}`.
(x) HOME :: `HOME` es tu directorio personal, no una lista de directorios de programas.
(x) PWD :: `PWD` contiene el directorio de trabajo actual.
@@note
`PATH` es una lista de directorios separados por dos puntos que se recorre de izquierda a derecha; gana la primera coincidencia.

@@q single | Ejecutar un programa fuera del PATH
Has escrito un script `tool.sh` en tu directorio actual y `.` no está en el `PATH`. ¿Qué mandato lo ejecuta (suponiendo que tiene permiso de ejecución)?
(+) `./tool.sh` :: Un nombre que contiene una barra se usa como ruta, así que no se busca en el `PATH`.
(-) `tool.sh` :: Sin barra, la shell solo busca en el `PATH`, no lo encuentra y responde `command not found`.
(-) `run tool.sh` :: No existe ese mandato estándar.
(-) `$tool.sh` :: Eso expande una variable llamada `tool` seguida de `.sh`; no ejecuta ningún fichero.

@@q single | Mandato no encontrado
Escribes `mytool` y obtienes `command not found`, pero `ls -l ./mytool` muestra un fichero ejecutable. ¿Cuál es la causa más probable?
(+) El directorio que lo contiene no está en el `PATH`, así que el nombre a secas nunca se busca ahí. :: Exacto. Usa `./mytool` o añade el directorio al `PATH`.
(-) El fichero necesita `sudo` para que la shell pueda verlo, aunque `ls` sí pueda listarlo. :: La falta de permisos produce `Permission denied`, no `command not found`.
(-) `ls` usa un `PATH` distinto del de la shell, así que encuentra ficheros que la shell no ve. :: `ls` no busca nada; le has dado una ruta.
(-) Los ficheros ejecutables solo están disponibles para la shell tras reiniciar o cerrar la sesión. :: No existe esa regla.

@@q order | Resolver la palabra del mandato
Ordena, del primero al último, los pasos con los que bash resuelve la primera palabra de un mandato simple.
(>) Expandir un alias si coincide alguno :: Los alias se sustituyen primero, antes de decidir nada más.
(>) Comprobar si hay una función de la shell con ese nombre :: Las funciones son definiciones propias de la shell y tienen prioridad sobre los programas en disco.
(>) Comprobar si hay un mandato interno con ese nombre :: Los internos forman parte de bash y se prueban antes de buscar en disco.
(>) Buscar un fichero ejecutable en los directorios del `PATH` :: Esta búsqueda en disco es el último recurso.

@@group Valor de retorno
@@q single | Significado del valor de retorno
¿Qué significa que un mandato devuelva un valor de retorno `0`?
(+) Que el mandato terminó con éxito. :: Por convenio, 0 es éxito y cualquier otro número indica algún tipo de fallo.
(-) Que el mandato no hizo nada. :: Un mandato puede hacer muchas cosas y aun así devolver 0.
(-) Que el mandato fue matado. :: Un proceso matado obtiene un valor mayor que 128 (128 más el número de la señal).
(-) Que el mandato se ejecutó en segundo plano. :: Ejecutar en segundo plano es otra cuestión y no tiene un valor especial.

@@q single | Leer el valor de retorno
¿Qué variable contiene el valor de retorno del último mandato?
(+) `$?` :: Contiene el valor del último mandato en primer plano que ha terminado.
(-) `$$` :: Contiene el identificador de proceso (PID) de la shell actual.
(-) `$!` :: Contiene el PID del último proceso lanzado en segundo plano.
(-) `$#` :: Contiene el número de argumentos de un script o de una función.

@@q match | Valores de retorno habituales
Empareja cada situación con el valor de retorno que indica bash.
(=) Un mandato se ejecutó y tuvo éxito => 0 :: Éxito.
(=) `ls /no/existe` falló => 2 :: El `ls` de GNU usa 2 para un problema serio, como una ruta inexistente.
(=) La palabra del mandato no se encuentra en ningún sitio => 127 :: El código especial de bash para `command not found`.
(=) El fichero existe pero no es ejecutable => 126 :: El código de bash para «encontrado pero no se puede ejecutar».
(-) 255 :: No corresponde a ninguna de estas situaciones; un proceso suspendido ni siquiera ha terminado, así que todavía no tiene valor.

@@q single | Valor tras un echo
Tras `false; echo $?` ves `1`. En la línea `echo hola; echo $?`, ¿qué imprime el segundo `echo`?
(+) `0`, el valor de retorno del primer `echo` :: `$?` siempre se refiere al mandato anterior, aquí el primer `echo`.
(-) `1`, el valor que quedó del `false` ejecutado antes :: Cada mandato que termina sobrescribe el valor guardado.
(-) `hola`, el texto que imprimió el primer mandato :: `$?` es un número, no la salida del mandato.
(-) Nada, porque `$?` está vacía hasta que termina un script :: Se actualiza tras cada mandato, también en el prompt.

@@q multi | Separadores según el valor de retorno
Marca las afirmaciones ciertas sobre `&&` y `||`.
(+) `a && b` ejecuta `b` solo si `a` tuvo éxito. :: `&&` significa «y después, si ha funcionado».
(+) `a || b` ejecuta `b` solo si `a` falló. :: `||` significa «si no».
(+) `a; b` ejecuta `b` sin importar cómo terminó `a`. :: El punto y coma simple ignora el valor de retorno.
(-) `a && b` ejecuta `b` solo si `a` falló. :: Ese es el comportamiento de `||`.
(-) `a || b` siempre ejecuta los dos mandatos. :: `b` se omite cuando `a` tiene éxito.

@@q single | Evaluar una cadena
¿Qué imprime `false && echo A || echo B`?
(+) `B` :: `false` falla, así que se omite `&& echo A`; el `||` ve un fallo y ejecuta `echo B`.
(-) `A` :: Para `A` haría falta que `false` tuviera éxito.
(-) `A` y después `B` :: `A` no se ejecuta nunca.
(-) Nada en absoluto :: La rama del `||` se ejecuta porque la parte izquierda no tuvo éxito.

@@q single | Éxito y luego fallo
¿Qué imprime `true && false || echo X`?
(+) `X` :: `true && false` termina con valor 1, así que se ejecuta la rama del `||`.
(-) Nada, porque `true` tuvo éxito. :: La cadena se evalúa de izquierda a derecha; el valor que llega al `||` es el de `false`.
(-) `true` :: Los internos `true` y `false` no imprimen nada; solo fijan el valor de retorno.
(-) Un error de sintaxis :: Mezclar `&&` y `||` es válido.

@@q fill | Comprobar y después actuar
Completa la línea para que `make` solo se ejecute si `cd build` tuvo éxito: `cd build {{&&}} make`
(x) ; :: Con `;`, make se ejecutaría aunque `cd build` fallara, en el directorio equivocado.
(x) || :: Eso ejecutaría `make` solo cuando `cd build` fallara, justo lo contrario de lo que se quiere.
@@note
`&&` es la forma segura de encadenar pasos que dependen unos de otros.

@@group Pedir ayuda: man, whatis, apropos, info
@@q single | Las secciones del manual
¿Qué número de sección del manual corresponde a los mandatos disponibles para usuarios normales (como `ls`)?
(+) 1 :: La sección 1 contiene los mandatos de usuario.
(-) 2 :: La sección 2 documenta las llamadas al sistema del núcleo.
(-) 5 :: La sección 5 describe formatos de fichero como `passwd`.
(-) 8 :: La sección 8 es para mandatos de administración del sistema que ejecuta root.

@@q match | Secciones del manual
Empareja cada sección con su contenido.
(=) Sección 1 => Mandatos de usuario :: Programas de uso diario como `ls` o `grep`.
(=) Sección 2 => Llamadas al sistema :: Funciones de la interfaz del núcleo, como `write(2)`.
(=) Sección 3 => Funciones de la biblioteca de C :: Rutinas de biblioteca como `printf(3)`.
(=) Sección 5 => Formatos de fichero y convenciones :: Por ejemplo `passwd(5)`.
(=) Sección 8 => Mandatos de administración del sistema :: Herramientas para root como `mount(8)`.
(-) Tutoriales de programación de scripts :: El manual no tiene sección de tutoriales; documenta mandatos, llamadas y formatos.

@@q single | Elegir una sección
`write` existe como mandato y como llamada al sistema. ¿Qué mandato abre la página de la **llamada al sistema**?
(+) `man 2 write` :: El número de sección va antes del nombre; la 2 son las llamadas al sistema.
(-) `man write 2` :: Bash pasa `2` como el nombre de una segunda página, no como sección.
(-) `man -2 write` :: No existe esa opción.
(-) `man write` :: Sin sección, man muestra la primera coincidencia, que es el mandato de usuario de la sección 1.

@@q single | Buscar por palabra clave
No sabes el nombre del mandato que comprime ficheros, pero recuerdas la palabra «compress». ¿Qué mandato la busca en las descripciones del manual?
(+) `apropos compress` :: Busca la palabra clave en los nombres y en las descripciones cortas.
(-) `whatis compress` :: Busca páginas cuyo *nombre* sea exactamente `compress`, así que ya tienes que saber el nombre.
(-) `whereis compress` :: Localiza los binarios y las páginas de un mandato conocido.
(-) `which compress` :: Solo muestra la ruta de un ejecutable que ya existe.

@@q multi | Formas equivalentes de buscar en el manual
Marca los mandatos que buscan una palabra clave en las descripciones de las páginas de manual.
(+) `apropos directory` :: Búsqueda por palabra clave en nombres y descripciones.
(+) `man -k directory` :: `-k` hace que `man` se comporte como `apropos`.
(-) `whatis directory` :: Solo encuentra páginas cuyo nombre sea `directory`.
(-) `info directory` :: Abre el documento info llamado `directory`; no es una búsqueda.

@@q single | Lo que imprime whatis
¿Qué imprime `whatis ls`?
(+) La descripción de una línea de cada página de manual que se llama `ls`. :: `whatis` es una consulta rápida de descripciones cortas por nombre exacto.
(-) El texto completo de la página de manual de `ls`, como hace `man ls` :: Eso es `man ls`.
(-) La ruta del ejecutable de `ls`, como hace `which ls` :: Eso es `which ls`.
(-) Todas las páginas cuya descripción menciona la palabra `ls` :: Eso sería `apropos ls`.

@@q fill | Abrir una página de manual
Para leer la página de manual del mandato `sort`, escribe: `{{man}} sort`
(x) help :: `help` documenta los mandatos *internos* de bash. `sort` es un programa externo, así que no tiene entrada en help.
(x) whatis :: Solo imprime un resumen de una línea, no la página.
@@note
`man nombre` abre la página en un paginador (normalmente `less`).

@@q single | Salir de man
¿Qué tecla cierra una página de manual mostrada por `man`?
(+) `q` :: `man` usa un paginador (`less`), donde `q` significa salir.
(-) `Ctrl+X` :: `less` no la usa.
(-) `Esc` :: Esc por sí sola no hace nada en `less`.
(-) `:wq` :: Eso es del editor vi, no de un paginador.

@@q single | Lo que aporta info
¿En qué se diferencian los documentos `info` de GNU de las páginas de manual?
(+) Son un árbol de nodos enlazados con menús y referencias cruzadas, no una única página larga y lineal. :: Esa estructura de hipertexto es la diferencia principal.
(-) Son resúmenes más cortos de las páginas de man, pensados para echar un vistazo rápido a las opciones. :: Suelen ser más largos y detallados.
(-) Los usuarios pueden editarlos y guardarlos, de modo que cada persona tiene su propia copia de la documentación. :: Son documentación de solo lectura.
(-) Solo se pueden leer en un entorno gráfico, porque el lector necesita un ratón para seguir los enlaces. :: El lector `info` estándar funciona en un terminal.

@@q match | Moverse por info
Empareja cada tecla del lector `info` con su acción.
(=) `n` => Siguiente nodo del mismo nivel :: Avanza en la secuencia de nodos hermanos.
(=) `p` => Nodo anterior del mismo nivel :: Retrocede en esa secuencia.
(=) `u` => Subir un nivel en el árbol :: Va al nodo padre.
(=) `l` => Volver al último nodo visitado :: Como el botón de atrás de un navegador.
(=) `q` => Salir de info :: Cierra el lector.
(-) Borrar el nodo actual :: No existe esa acción; los documentos info son de solo lectura.

@@q single | Entradas de menú en info
En una página de `info`, ¿cómo sigues un enlace que aparece como `* Common options::`?
(+) Pones el cursor encima y pulsas Intro. :: Intro salta al nodo al que apunta la entrada de menú o la referencia cruzada.
(-) Pulsas `Ctrl+C`. :: Eso envía una interrupción y no sigue enlaces.
(-) Escribes su nombre detrás de `man`. :: `man` no sabe nada de los nodos de info.
(-) Los enlaces no se pueden seguir; las páginas de info son texto plano. :: Seguir enlaces es justo lo que hace que info sea hipertexto.

@@group Leer textos largos con less
@@q single | Por qué less
¿Por qué `man` muestra las páginas a través de `less` en lugar de imprimirlas sin más?
(+) `less` muestra una pantalla cada vez y te deja desplazarte y buscar hacia delante y hacia atrás. :: Un paginador hace legible un texto largo.
(-) `less` traduce la página a tu idioma y la formatea para que encaje en el ancho del terminal. :: Solo muestra texto.
(-) `less` protege las páginas para que no se modifiquen, cosa que imprimir directamente en pantalla no haría. :: La protección viene de los permisos del fichero, no del paginador.
(-) Porque un terminal no puede imprimir más de 24 líneas sin perder el resto de la salida. :: Los terminales pueden desplazarse; el paginador es por comodidad.

@@q match | Teclas de less
Empareja cada tecla de `less` con lo que hace.
(=) `Espacio` => Avanzar una pantalla :: Página abajo.
(=) `b` => Retroceder una pantalla :: Página arriba.
(=) `g` => Saltar a la primera línea :: Ir al principio del texto.
(=) `G` => Saltar a la última línea :: Ir al final del texto.
(=) `/palabra` => Buscar `palabra` hacia delante :: Encuentra la siguiente coincidencia más abajo.
(=) `?palabra` => Buscar `palabra` hacia atrás :: Encuentra la coincidencia anterior más arriba.
(=) `n` => Repetir la última búsqueda :: Siguiente coincidencia en el mismo sentido.

@@q fill | Buscar dentro de un manual
Dentro de una página de man, al escribir `{{/}}error` empieza una búsqueda hacia delante de la palabra error, y al pulsar `{{n}}` saltas a la siguiente coincidencia.
(x) ? :: `?` también busca, pero hacia atrás.
@@note
`/` busca hacia delante, `?` busca hacia atrás, `n` repite y `N` repite en sentido contrario.

@@q single | less frente a more
Comparado con el antiguo `more`, ¿qué ventaja tiene `less`?
(+) Puedes desplazarte hacia atrás además de hacia delante, y buscar en ambos sentidos. :: Esa flexibilidad le dio su nombre, como broma sobre «less is more».
(-) Puede editar el fichero mientras lo ves y guardar los cambios con una sola tecla. :: Ninguno de los dos es un editor.
(-) Es el único paginador que funciona en una tubería, porque `more` necesita un nombre de fichero. :: Los dos pueden leer de una tubería.
(-) Ordena automáticamente las líneas del texto antes de mostrarlas página a página. :: Ordenar es trabajo de `sort`.

@@group Edición de línea y teclas de la shell
@@q multi | Teclas de edición de línea en bash
Marca las teclas que funcionan en el prompt de bash tal como se describe.
(+) `Tab` completa el nombre de un mandato o de un fichero. :: Completar ahorra escribir y evita erratas.
(+) `↑` recupera el mandato anterior del historial. :: Cada pulsación retrocede un poco más.
(+) `Ctrl+A` salta al principio de la línea que estás escribiendo. :: Las teclas de edición al estilo Emacs son las predeterminadas en bash.
(+) `Ctrl+E` salta al final de la línea que estás escribiendo. :: La pareja de `Ctrl+A`.
(-) `Ctrl+Z` borra toda la línea que estás escribiendo :: `Ctrl+Z` suspende el mandato en ejecución; no edita nada.

@@q single | Búsqueda inversa
¿Qué hace `Ctrl+R` en el prompt de bash?
(+) Inicia una búsqueda incremental hacia atrás en tu historial de mandatos. :: Escribe unas letras y aparece el mandato más reciente que coincide; vuelve a pulsarla para ver otros más antiguos.
(-) Vuelve a ejecutar al momento el mandato anterior, sin mostrarlo para editarlo. :: Repetir el último mandato es `!!`.
(-) Vuelve a cargar la configuración de la shell, como `~/.bashrc`, en la shell actual. :: Recargar es `source ~/.bashrc`.
(-) Elimina el último mandato del historial para que no se pueda recuperar de nuevo. :: `Ctrl+R` solo busca.

@@q match | Teclas que actúan sobre el programa en ejecución
Empareja cada tecla con su efecto.
(=) `Ctrl+C` => Interrumpir (normalmente terminar) el mandato en primer plano :: Envía `SIGINT` al trabajo en primer plano.
(=) `Ctrl+Z` => Suspender el mandato en primer plano :: Envía `SIGTSTP`; el trabajo queda detenido, no muerto.
(=) `Ctrl+D` => Indicar fin de la entrada (EOF) :: Con el prompt vacío, además cierra la shell.
(=) `Ctrl+L` => Limpiar la pantalla :: El mismo efecto que el mandato `clear`.
(-) Borrar la última palabra :: Eso es `Ctrl+W`. Ninguna de las teclas de arriba lo hace.

@@q single | Expansión del historial
Tras ejecutar `ls /etc`, ¿qué hace escribir `!!` y pulsar Intro?
(+) Repite el mandato anterior, `ls /etc`. :: `!!` se expande a la última línea de mandatos.
(-) Imprime el historial de mandatos. :: Eso es el mandato `history`.
(-) Cancela el mandato anterior. :: Un mandato que ya ha terminado no se puede cancelar.
(-) Niega el valor de retorno del mandato anterior. :: Eso lo hace un `!` suelto al principio del mandato; `!!` es historial.

@@group Leer una línea de mandatos
@@q single | Anatomía de un mandato
En `ls -l /etc`, ¿qué son `-l` y `/etc`?
(+) Dos argumentos que se pasan a `ls`: una opción y un operando. :: La shell divide la línea en palabras; la primera es el mandato y el resto son sus argumentos.
(-) Dos mandatos distintos; el segundo es `/etc`, que se ejecuta después de `ls`. :: Solo la primera palabra es el mandato.
(-) Dos variables de entorno que `ls` lee para decidir qué listar y dónde. :: Las variables se asignan con `NOMBRE=valor`.
(-) Comentarios que la shell ignora y que `ls` nunca ve en su lista de argumentos. :: Los comentarios empiezan por `#`.

@@q single | División por espacios
¿Cuántos argumentos pasa `echo a    b` (con cuatro espacios en medio) a `echo`, y qué imprime?
(+) Dos argumentos, `a` y `b`; imprime `a b` con un solo espacio. :: La shell divide por grupos de blancos, y `echo` une los argumentos con un espacio.
(-) Un argumento, que imprime como `a    b` con los cuatro espacios. :: Para eso hacen falta comillas: `echo "a    b"`.
(-) Tres argumentos, porque el grupo de espacios cuenta como un argumento más. :: Los blancos son separadores, no argumentos.
(-) Falla, porque `echo` no admite espacios de más entre argumentos. :: Los blancos de más simplemente se ignoran.

@@q single | Las comillas dobles conservan los espacios
¿Qué imprime `echo "a    b"`?
(+) `a    b`, con los cuatro espacios exactamente como se escribieron. :: Las comillas impiden la división en palabras, así que `echo` recibe un solo argumento.
(-) `a b`, con los espacios reducidos a uno :: Ese es el resultado sin comillas.
(-) `"a    b"`, incluidas las propias comillas :: La shell quita las comillas antes de que `echo` vea el argumento.
(-) Nada, porque las comillas dentro de `echo` son un error :: Entrecomillar es perfectamente válido.

@@q fill | Comentarios
Todo lo que va detrás de un carácter `{{#}}` que empieza una palabra es un comentario y bash lo ignora.
(x) // :: `//` es un comentario en lenguajes tipo C, pero en bash es solo texto.
(x) -- :: `--` sirve para terminar las opciones; no es un comentario.
@@note
En los scripts, un `#` al principio de una palabra inicia un comentario; un `#` dentro de una palabra, como en `a#b`, es texto normal.

@@q single | Primera palabra de un mandato
En `FOO=bar env | grep FOO`, ¿cómo trata la shell `FOO=bar`?
(+) Como una asignación de variable que se coloca solo en el entorno del mandato `env`. :: Las asignaciones delante del nombre de un mandato son temporales y solo afectan a ese mandato.
(-) Como el nombre del mandato que hay que ejecutar, con `env` y `grep` como argumentos. :: Un `NOMBRE=valor` al principio se reconoce como asignación, no como mandato.
(-) Como un error, porque una asignación tiene que ir sola en su propia línea. :: Las asignaciones delante de un mandato son válidas.
(-) Como un cambio permanente en el entorno de tu shell actual. :: La asignación desaparece cuando termina el mandato.

@@group La sesión y el prompt en la práctica
@@q single | Salir de la shell
¿Qué forma termina una sesión interactiva de bash?
(+) Escribir `exit`, o pulsar `Ctrl+D` con el prompt vacío. :: Las dos terminan la shell; `Ctrl+D` envía fin de entrada.
(-) Pulsar `Ctrl+C` con el prompt vacío, lo que interrumpe a la propia shell. :: Eso solo te da un prompt nuevo.
(-) Pulsar `Ctrl+Z`, que suspende la shell y cierra el terminal. :: Eso suspende el trabajo en primer plano; con el prompt vacío no hace nada útil.
(-) Escribir `quit`, que es el equivalente de `exit` en bash. :: Bash no tiene ningún mandato `quit`.

@@q single | Mandatos largos en varias líneas
¿Qué hace una barra invertida justo al final de una línea en bash?
(+) Escapa el salto de línea, así que el mandato continúa en la línea siguiente. :: Muy práctico para partir mandatos largos y que se lean mejor.
(-) Termina el mandato en ese punto y muestra un error de sintaxis al usuario. :: Una barra invertida al final es válida.
(-) Imprime una barra invertida literal y luego empieza un mandato nuevo y separado. :: La pareja barra invertida + salto de línea se elimina antes de ejecutar.
(-) Ejecuta el mandato en segundo plano para que el prompt vuelva enseguida. :: Eso es trabajo de `&`.

@@q single | En qué shell estoy
¿Qué mandato muestra el nombre del programa de shell que estás ejecutando (en una sesión típica de bash)?
(+) `echo $0` :: `$0` se expande al nombre de la shell en ejecución (por ejemplo `bash`).
(-) `echo $#` :: `$#` es el número de argumentos, no el nombre de un programa.
(-) `echo $?` :: Eso imprime el último valor de retorno.
(-) `echo $HOME` :: Eso imprime tu directorio personal.

@@q single | El valor de retorno en el prompt
¿Por qué mucha gente muestra el último valor de retorno en su prompt?
(+) Para darse cuenta al momento de que el mandato anterior falló, sin tener que escribir `echo $?`. :: Es una información útil cuando encadenas muchos mandatos.
(-) Porque bash no deja ejecutar otro mandato tras uno fallido hasta que lo confirmas. :: Bash no bloquea nada; todos los mandatos se ejecutan igualmente.
(-) Porque el valor de retorno decide qué usuario será el propietario del siguiente fichero que crees. :: La propiedad de los ficheros no tiene nada que ver con el valor de retorno.
(-) Porque POSIX exige que todo prompt interactivo muestre el último valor de retorno. :: Ningún estándar lo exige; es una comodidad.

@@group Predice el resultado
@@q single | La sorpresa del punto y coma sin comillas
¿Qué pasa al ejecutar `echo a;b` (sin espacios ni comillas)?
(+) Se imprime `a` y después bash avisa de que no encuentra `b` como mandato. :: El `;` divide la línea en `echo a` y `b`; después `b` se busca como nombre de mandato.
(-) Se imprime `a;b` en una línea, porque las dos letras forman un único argumento. :: Para eso harían falta comillas: `echo "a;b"`.
(-) Se imprimen `a` y `b` en líneas distintas, una por cada mandato. :: `b` es un mandato, no un texto que imprimir, así que se busca en el `PATH`.
(-) Bash muestra un error de sintaxis cerca de `;` y no ejecuta nada. :: La línea es sintácticamente válida; el fallo se produce al ejecutar `b`.

@@q single | Valor tras un cd fallido
Si `cd /noexiste` falla, ¿qué imprime `echo $?` justo después?
(+) Un número distinto de cero (1 en bash). :: `cd` falló, y un fallo es cualquier valor distinto de cero.
(-) `0`, porque `cd` imprimió su mensaje correctamente. :: Imprimir un mensaje de error no hace que un mandato tenga éxito.
(-) El nombre del directorio actual. :: `$?` solo contiene un número.
(-) Nada, porque los mandatos internos que fallan no actualizan `$?`. :: Todos los mandatos, internos o no, la actualizan.

@@q single | Valor de retorno de una subshell
¿Qué imprime `bash -c "exit 3"; echo $?`?
(+) `3` :: La shell hija terminó con `exit 3` y la shell padre guardó ese número en `$?`.
(-) `0`, porque la propia shell padre no falló. :: `$?` informa del mandato hijo que acaba de terminar, no del padre.
(-) `exit 3` :: `$?` es un número, nunca el texto del mandato.
(-) Nada: `exit` solo funciona en scripts. :: `bash -c` ejecuta una cadena de mandatos como un pequeño script, así que `exit` funciona.

@@q multi | Formas de obtener ayuda sobre un mandato
Marca las formas de ver documentación del mandato `grep` en un Linux típico.
(+) `man grep` :: Abre la página de manual.
(+) `grep --help` :: La mayoría de programas GNU imprimen un resumen de uso con `--help`.
(+) `info grep` :: Abre el manual de info, si está instalado.
(-) `type grep` :: Muestra cómo se resuelve el nombre (por ejemplo su ruta), no documentación.
(-) `which grep` :: Solo imprime la ruta del ejecutable.

@@q single | Ayuda de un mandato interno
`cd` es un mandato interno de bash y no tiene un programa aparte. ¿Qué mandato imprime su texto de ayuda?
(+) `help cd` :: `help` es un mandato interno de bash que documenta los internos de la propia shell.
(-) `grep cd` :: Eso buscaría el texto `cd` en la entrada estándar.
(-) `whereis cd` :: Busca ficheros; un mandato interno no tiene ninguno.
(-) `cd --help` :: `cd` lo toma como nombre de directorio y falla.

@@q multi | Lo que indica whereis
¿Qué información puede imprimir `whereis ls`?
(+) La ubicación del ejecutable de `ls`. :: Busca en los directorios estándar de binarios.
(+) La ubicación de la página de manual de `ls`. :: También busca en los directorios del manual.
(-) El valor de retorno de la última ejecución de `ls`. :: No sabe nada de ejecuciones anteriores.
(-) La lista de ficheros del directorio actual. :: Eso es lo que hace ejecutar el propio `ls`.

@@q single | Cancelar una línea a medio escribir
Has escrito parte de un mandato y cambias de idea. ¿Qué combinación de teclas descarta la línea y te da un prompt nuevo?
(+) `Ctrl+C` :: En el prompt descarta lo escrito y empieza una línea nueva.
(-) `Ctrl+Z` :: Suspende programas en ejecución; en el prompt no borra la línea.
(-) `Ctrl+D` :: Con la línea no vacía no hace nada útil (y con la línea vacía cierra la shell).
(-) `Ctrl+L` :: Limpia la pantalla pero conserva la línea que escribiste.

@@q single | if comprueba el valor de retorno
¿Qué comprueba `if grep -q root /etc/passwd; then echo sí; fi`?
(+) Si `grep` termina con valor 0, es decir, si encontró alguna coincidencia. :: `if` ejecuta el mandato y decide según su valor de retorno.
(-) Si `grep` imprime el texto `root` en la pantalla. :: Con `-q`, grep no imprime nada; solo importa el valor de retorno.
(-) Si `/etc/passwd` existe y es un fichero regular que se puede leer. :: Solo indirectamente: si no se puede leer, grep falla.
(-) Si se ha definido una variable de la shell llamada `root`. :: No interviene ninguna variable.

@@q single | Orden de evaluación
¿Qué líneas imprime `true || echo X; false || echo Y; true && echo Z`?
(+) `Y` y `Z` :: `X` se omite porque `true` tuvo éxito; `false` falla, así que se ejecuta `Y`; `true` tiene éxito, así que se ejecuta `Z`.
(-) `X`, `Y` y `Z` :: `||` no ejecuta su parte derecha tras un éxito.
(-) `X` y `Z` :: Para `X` haría falta que la parte izquierda fallara.
(-) Nada :: Dos de las tres partes derechas sí se ejecutan.

@@q single | Ruta frente a nombre
`/bin/ls` y `ls` ejecutan el mismo programa en la mayoría de sistemas. ¿Qué diferencia hay en cómo lo encuentra bash?
(+) Una palabra con barra se usa directamente como ruta; un nombre a secas se busca en el `PATH`. :: Una palabra que contiene `/` se salta por completo el orden de búsqueda.
(-) `/bin/ls` es más lento, porque ejecutar un programa por su ruta completa requiere privilegios de root. :: No hace falta ningún privilegio para ejecutarlo por su ruta.
(-) No hay ninguna diferencia: bash siempre busca en el `PATH`, aunque la palabra contenga una barra. :: Una palabra con barra nunca se busca en el `PATH`.
(-) `ls` ejecuta la versión interna del mandato y `/bin/ls` ejecuta el programa externo. :: `ls` no es un mandato interno de bash.
